<objective>
**As an** Architect looking at an EAM diagram, **I want to** see a small fill/ring marker on each application, AI component, and infrastructure element showing whether it is itself the cause of a sovereignty violation or only affected by something weaker downstream, **so that** I can spot canonical sovereignty problems visually on the diagram I already use, without opening every element's detail dialog (per ROADMAP.md Phase 2 Success Criteria #5).

This plan is the client-only diagram integration that consumes 02-02's `sovereigntyMarkers` batch GraphQL query and renders the D-05 two-marker (fill/ring) model on diagram canvas elements, gated behind the existing `featureFlags.Sovereignty` flag (D-09), wired into the existing `syncDiagramOnOpen` pipeline. It does not touch any server/backend code (02-01/02-02/02-04) or the element-detail views (02-03).

Purpose: make Phase 2 Success Criteria #5 true end-to-end on the client — enabling the flag makes real elements show canonical status markers that visually distinguish local violations from downstream impact.
Output: `client/src/graphql/sovereigntyMarkers.ts` (query), `client/src/components/diagrams/utils/sovereigntyMarkers.ts` (fetch + transform + gated orchestration), and two small wiring edits to the existing diagram-open/sync pipeline.
</objective>
