## Accomplishments

- `createMarkerEllipses`'s shared `base` object now sets `locked: true` (was `false`) — marker ellipses are excluded from Excalidraw's own click/drag/group-co-selection at the interaction layer (D-04), with `repositionMarkerEllipses`/`repositionAllMarkerEllipses` left byte-for-byte unmodified.
- `ExcalidrawWrapper.tsx`'s `handleChange` gained diff-based new-main-element detection (`previouslySeenMainElementIdsRef`): a genuinely new, non-deleted main element (library drop, duplicate, copy/paste) triggers the existing `syncSovereigntyMarkers` fetch+apply pipeline exactly once, with zero extra GraphQL calls on ordinary drag/pan/edit of already-seen elements (D-02).
- New exported `removeOrphanedMarkersLive()` in `sovereigntyMarkers.ts` fixes the `isDeleted` gap in the existing sync-time orphan-detection loop for the live/incremental onChange context, tombstoning (not array-filtering) orphaned markers when their main element is natively keyboard-deleted; wired into `handleChange` with `captureUpdate: CaptureUpdateAction.IMMEDIATELY` (D-01/D-03).
- The pre-existing `repositionAllMarkerEllipses` `updateScene` call's stale two-argument form (`{ elements }, false`) was replaced with the single-object form + explicit `captureUpdate: CaptureUpdateAction.EVENTUALLY`, matching the installed `@excalidraw/excalidraw@0.18.1` API surface.
- `applySovereigntyMarkers` itself is completely unmodified (verified via diff — only additions after it in the file).

## Decisions Made

- Task 2's auto-add follow-up `updateScene` call uses `captureUpdate: CaptureUpdateAction.EVENTUALLY`, per the plan's explicit instruction — this differs from RESEARCH.md Pattern 1's illustrative code example (`NEVER`); the plan's literal action text was treated as authoritative over the research pattern's example.
- Task 3's orphan-cleanup `updateScene` call uses `captureUpdate: CaptureUpdateAction.IMMEDIATELY`, per RESEARCH.md Pitfall 1's two-tier strategy — this is a deliberate, documented choice: native keyboard delete will require **two** Ctrl+Z presses to fully restore both the element and its markers (first pop restores the marker-cleanup entry, second pop restores the delete itself). This is correct, self-contained behavior per the research, not a bug — **the actual keystroke count was not verified in this session** (see Manual Verification Deferred, below).
- `Array.from(currentMainElementIds)` used instead of the plan/research's `[...currentMainElementIds]` spread — the project's TS target/lib does not support spreading a `Set` without `--downlevelIteration` (`TS2802`); functionally identical.
