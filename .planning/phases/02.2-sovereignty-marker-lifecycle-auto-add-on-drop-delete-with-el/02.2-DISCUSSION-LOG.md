## Auto-add trigger mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| Diff-based: only fetch for genuinely new main elements | Detect new isMainElement+databaseId entries not seen on the previous onChange pass, then reuse the existing syncSovereigntyMarkers fetch+apply pipeline only for those | ✓ |
| Naive: re-fetch on every onChange | Simpler code, but would issue redundant GraphQL marker queries on every drag/pan/edit, not just drop | |
| Debounced batching | Detect immediately but wait a short idle window (~300-500ms) before fetching, coalescing rapid multi-drops/pastes into one query | |

**User's choice:** Diff-based: only fetch for genuinely new main elements
**Notes:** No GraphQL calls during pure drags/pans/edits — only when a genuinely new main element appears. Debounce on top of diffing left as the agent's discretion, not re-opened as a separate decision.

## Undo/redo after delete

| Option | Description | Selected |
|--------|-------------|----------|
| Markers reappear automatically on undo | Requires folding marker removal into the same Excalidraw-tracked history entry as the element delete, so Ctrl+Z restores element + markers together | ✓ |
| Acceptable to stay marker-less until next resync | Simpler: cleanup runs outside Excalidraw's undo stack; undo restores the element but it stays marker-less until next resync | |

**User's choice:** Markers reappear automatically on undo
**Notes:** User chose the more robust (costlier) option — flagged in CONTEXT.md with a `Reversibility: costly` rating since it requires the cleanup step to be undo-aware, not a simple side-channel filter.

## Non-selectability mechanism

| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** locked: true on marker ellipses
**Notes:** Simplest, Excalidraw-native mechanism. Research flagged: markers share `groupIds: [mainElement.id]` with their main element — needs confirming whether `locked: true` removes them from that group-selection coupling too; if so, the onChange-based cleanup becomes the sole delete-cleanup mechanism, which is the safe planning assumption per D-04.
