# Phase 02.2: Sovereignty marker lifecycle: auto-add on drop, delete with element, non-selectable - Context

**Gathered:** 2026-07-31
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase keeps sovereignty diagram markers (fill/ring ellipses, delivered in Phase 2 and made reload/drag-safe in Phase 02.1) correctly synced through the rest of the element lifecycle on a diagram — not just at open/reload time. Specifically:

1. **Auto-add on drop:** dragging a new main element onto the canvas from the library must get its fill/ring markers applied immediately, without requiring a manual Ctrl+R resync.
2. **Delete with element:** deleting a main element must instantly remove its associated marker ellipses in the same change, instead of leaving orphaned markers behind.
3. **Research + confirm/fix non-selectability:** marker ellipses must be excluded from direct selection (not independently selectable/draggable/deletable by the user).
4. **Research other lifecycle events** not yet covered (copy/paste, duplicate, undo/redo of a delete, group operations) and surface any additional gaps found — see D-01 for how much of this must be *fixed* this phase vs. only *documented*.

This phase does not touch the canonical sovereignty evaluator, the marker query/GraphQL contract, or the reload-sync/live-drag-reposition mechanisms Phase 02.1 already fixed — it extends the same mechanisms to more lifecycle events.

</domain>

<decisions>
## Implementation Decisions

### Lifecycle fix scope
- **D-01 [USER-CONFIRMED 2026-07-31]:** For lifecycle gaps beyond the two named items (copy/paste, duplicate, undo/redo-of-delete, group operations) — handle **case-by-case**: if research/planning confirms a gap and it's cheap/trivial to fix (e.g. a one-line change reusing existing logic), fix it in this phase. If a confirmed gap is non-trivial (needs new mechanism, meaningfully widens scope), log it as a finding/backlog item instead of fixing it now. This is a middle ground between "fix everything found" and the ROADMAP's literal "surface as findings" wording — the user explicitly rejected both extremes in favor of judgment per gap. Planner/executor should record the triviality call and rationale for each gap encountered.

### Auto-add trigger mechanism
- **D-02 [USER-CONFIRMED 2026-07-31]:** The auto-add-on-drop fetch must be **diff-based**: detect when a genuinely new main element (`customData.isMainElement && customData.databaseId`) appears in the elements array that wasn't present on the previous onChange pass, and only then invoke the existing `syncSovereigntyMarkers`/`fetchSovereigntyMarkersForDiagram` + `applySovereigntyMarkers` fetch+apply pipeline (reused as-is, not reimplemented) for the diagram's current roots. Explicitly rejected: re-running the fetch on every onChange regardless of whether anything new was added (onChange fires on every drag/pan/edit — the user chose not to add GraphQL calls for those). Debounced batching of rapid multi-drops was also considered and not chosen — diff-based detection is the locked mechanism; whether the executor also adds a light debounce as an implementation detail for very rapid successive drops is the agent's discretion, not a re-opened decision.

### Undo/redo after delete
- **D-03 [USER-CONFIRMED 2026-07-31]:** When a delete removes a main element's markers (per the required delete-with-element fix), pressing Ctrl+Z (undo) must **restore the markers automatically**, not leave a marker-less gap until the next resync. — **Reversibility:** costly — this requires the marker-cleanup step to be folded into the same Excalidraw-tracked change/history entry as the element delete (or otherwise made undo-aware), not a side-channel cleanup that runs outside Excalidraw's own undo stack. If implemented as a bolt-on filter outside the undo history, undoing a delete would resurrect the element without its markers, contradicting this decision — revisiting this later means re-architecting how the delete-cleanup hooks into Excalidraw's change/undo pipeline, not just editing one function.

### Non-selectability mechanism
- **D-04 [USER-CONFIRMED 2026-07-31]:** Marker ellipses must be made non-selectable/non-draggable/non-deletable via **`locked: true`** on both the fill and ring ellipse elements (currently `locked: false` in `createMarkerEllipses` in `sovereigntyMarkers.ts` — very likely the literal cause of markers being directly clickable/draggable today). Explicitly rejected: building custom pointer-event/selection-filtering logic instead of using Excalidraw's native flag. Research/planning must verify `locked: true` does not block the existing programmatic `repositionMarkerEllipses`/`repositionAllMarkerEllipses` `updateScene()` calls from Phase 02.1 (those are programmatic writes, not user pointer interactions, so should be unaffected — but this needs confirming, not assuming) and must research whether `locked: true` removes marker ellipses from the shared-`groupIds` co-selection with their main element (see Code Context below) — if so, the explicit onChange-based delete-cleanup (D-01/existing orphan-detection logic in `applySovereigntyMarkers`) becomes the sole cleanup mechanism regardless of native group-delete behavior, which should be treated as the safe assumption during planning.

### the agent's Discretion
- Exact mechanism for diffing "new main elements" between onChange passes (e.g. maintaining a ref/Set of previously-seen main element ids vs. some other tracking approach) — implementation detail for planning.
- Whether to add a light debounce on top of D-02's diff-based detection for rapid successive drops — allowed but not required.
- Per-gap triviality judgment calls under D-01's case-by-case rule — planner/executor decide and document rationale per gap found.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `syncSovereigntyMarkers`/`fetchSovereigntyMarkersForDiagram` (`sovereigntyMarkers.ts`) — already handles multi-root querying, worst-status merging, and the `featureFlags.Sovereignty`/`companyId` gate (D-09 from Phase 2). D-02 reuses this verbatim for auto-add; no new fetch logic needed, only new trigger wiring.
- `applySovereigntyMarkers`'s existing orphan-detection (`isOrphaned` check against `presentMainElementIds`) — this is already the exact logic needed for delete-cleanup; it just needs to run live on every relevant onChange instead of only at full sync/reload/manual-resync.
- `suppressOnChangeRef` guard pattern already used in `ExcalidrawWrapper.tsx`'s `handleChange` for the D-02/D-03 (Phase 02.1) live-reposition `updateScene()` calls — the established, safe way to make a programmatic scene update without re-triggering an infinite onChange loop; the new auto-add/delete-cleanup logic should follow the same pattern.

### Established Patterns
- Every marker element carries `customData.mainElementId` linking it back to its main element, and `customData.sovereigntyMarker: 'fill' | 'ring'` identifying its role — the existing, sufficient linkage for all lifecycle detection logic in this phase (no new customData fields needed).
- Marker ellipses and their main element currently share `groupIds: [mainElement.id]` (the main element's own id doubles as the shared group id) — this is a *softer* coupling than direct selection and may already cause markers to be implicitly co-selected/co-dragged/co-deleted as part of Excalidraw's native group semantics when the user selects the main element. This is distinct from the direct-independent-click problem D-04 targets, and needs research: does `locked: true` remove them from this group membership too? If so, the onChange-based cleanup (D-01) must be the sole delete-cleanup mechanism regardless of any native group-delete behavior — treat this as the safe planning assumption per D-04.
- `createExcalidrawElementFromLibraryItem` (`excalidrawLibraryUtils.ts`) appears to be **dead/unused code** for the actual drop path — grep found only its own definition, no call sites. The real drop mechanism goes through Excalidraw's native `EXCALIDRAW_LIBRARY_MIME` drag payload (`DiagramLibrarySidebar.tsx`), which Excalidraw itself materializes into scene elements internally. Research should confirm this before assuming `createExcalidrawElementFromLibraryItem`'s `isMainElement`/`groupIds` shape is what actually lands on the canvas after a drop.

### Integration Points
- `ExcalidrawWrapper.tsx`'s existing `handleChange` (wrapping the raw Excalidraw `onChange`) is the single integration point for both new behaviors (D-02 auto-add detection, D-01 live delete-cleanup) — no new event wiring needed, same as Phase 02.1's live-reposition feature.
- Whatever undo/redo mechanism D-03 requires must integrate with Excalidraw's own history stack (likely via how `updateScene` calls are sequenced/tagged), not bypass it — a planning-time research concern.
