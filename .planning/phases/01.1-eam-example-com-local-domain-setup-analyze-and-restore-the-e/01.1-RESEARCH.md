# Phase 01.1: eam.example.com local domain setup - Research

**Researched:** 2026-07-27
**Domain:** Local Docker Compose hostname routing via an externally-managed Traefik reverse proxy, in front of a Keycloak-backed OIDC login flow
**Confidence:** HIGH

## Summary

The `eam.example.com` Optional Path is broken today for one simple, verifiable reason: **no Traefik container exists on this machine** (`docker ps -a --filter name=traefik` returns empty), even though the `traefik` external Docker network exists and 6 containers (`client`, `server`, `keycloak`, `neo4j`, `excalidraw-room`, `temporal-ui`) are already attached to it and already carry correct Traefik routing labels. `.env` is byte-for-byte identical to `env.template` (`diff` returns no output) — `BASE_DOMAIN=example.com`, `TRAEFIK_NETWORK=traefik`, `TRAEFIK_CERTRESOLVER=my-traefik-cert-resolver` (a placeholder, not empty). `/etc/hosts` has no entry for `eam.example.com` or any sibling subdomain — only an unrelated `127.0.1.1 eam.wien.arthofer.dev eam` line from another project (PVE-managed), which does not collide with `example.com` FQDNs.

Restoring the path requires three independent fixes, not just "start a Traefik container":

1. **Start a local Traefik instance** attached to the pre-existing external `traefik` network (do not touch `compose.yml` — D-04/D-05). Existing Traefik labels in `compose.yml` are correct and sufficient as-is; no label changes are needed.
2. **Set `TRAEFIK_CERTRESOLVER=` (empty) in `.env`** so no local Traefik logs errors trying to resolve a real ACME certificate for `example.com` (a domain the developer doesn't control) — Traefik falls back to its built-in self-signed default certificate for any router whose declared resolver isn't registered `[CITED: doc.traefik.io/traefik/v3.0/https/tls]`.
3. **Give container-to-container calls a way to resolve `auth.example.com`** — this is the non-obvious root cause the CONTEXT.md evidence doesn't fully explain. The `server` container's own JWKS/token-validation code calls `https://auth.example.com/realms/.../certs` directly using `process.env.KEYCLOAK_URL` (verified in [server/src/graphql/schema.ts](../../../server/src/graphql/schema.ts) and [server/src/auth/auth-jwks.ts](../../../server/src/auth/auth-jwks.ts)). Docker containers do **not** inherit the host's `/etc/hosts` file `[CITED: docs.docker.com/engine/network — "Custom hosts... aren't inherited by containers"]`, and a custom-network container's DNS lookups for names Docker doesn't recognize are forwarded to the **host's upstream DNS resolvers**, not the host's hosts file `[CITED: docs.docker.com/engine/network — "DNS services"]`. Since `example.com` is a real, publicly resolvable IANA reserved domain, the `server` container would silently resolve `auth.example.com` to the real internet — not the local Traefik — and JWKS validation (hence all authenticated GraphQL calls) would fail even after fixing (1) and (2). The fix is to give the **local Traefik container itself** Docker network aliases for every subdomain on the shared network with the backend services, so any container on that same network (including `server`) resolves `auth.example.com` via Docker's embedded DNS straight to the local Traefik container.

## Verified Prior Art (Supersedes Pattern 2 below — UPDATE, HIGH confidence)

**Source:** A sibling checkout of this project (`~/simpleEAM`, remote `DE-FUE-CTO-COMMUNITY/simpleEAM` — a different fork of the same codebase family) contains an **uncommitted but proven-working** local Traefik/HTTPS testbed, discovered and pulled into this phase's plan on 2026-07-27. `compose.yml` in that checkout is byte-identical to this repo's (`diff` confirmed), so the mechanism transfers directly.

This working implementation **corrects two assumptions** made earlier in this research session, based on concrete first-hand evidence rather than inference:

1. **D-06/D-07 correction — a locally-generated CA + wildcard certificate is required, not merely optional/deferred.** Traefik's auto-generated self-signed default certificate (Pattern 2, original recommendation) is sufficient for a *browser*, which lets a user click through a TLS warning. It is **not** sufficient for the `server`/`analytics-worker`/`client` containers' own outbound HTTPS calls (Node.js's `https`/`fetch` client, used for the JWKS fetch in `server/src/auth/auth-jwks.ts`) — Node hard-fails with `UNABLE_TO_VERIFY_LEAF_SIGNATURE` against an untrusted self-signed cert; there is no "click through" for a server-side TLS client. The proven fix: generate a local root CA once (`local/make-local-ca.sh`, idempotent, produces `rootCA.pem`/`rootCA.key` + a `*.example.com` wildcard cert signed by it), have Traefik present the wildcard cert (via a `file` provider + `defaultCertificate`, no ACME), and mount `rootCA.pem` into `server`/`analytics-worker`/`client` with `NODE_EXTRA_CA_CERTS` so Node explicitly trusts it. D-07's "mkcert is optional, not required" framing was based on an incomplete picture (browser-only view of the problem) — this is a factual correction, not a re-opened scope decision.
2. **Network aliases belong on `eam-network` (the app's internal Compose network), not the external `traefik` network.** The working example joins the local Traefik container to *both* `traefik` (so Traefik's Docker provider can discover the existing router labels) *and* `eam-network` (with the 6 subdomain aliases). This means backend services never need to join the external `traefik` network themselves to resolve `auth.example.com` — they already sit on `eam-network` by default. Simpler and one fewer moving part than the originally proposed alias placement.
3. **`docker-compose.override.yml` (not a separately-named, `-f`-flagged file) is the correct mechanism.** Docker Compose auto-merges `docker-compose.override.yml` (or `compose.override.yaml`) alongside the base file with a plain `docker compose up -d` — verified working (`docker compose config --quiet` merges cleanly with this repo's `compose.yml`, exit 0). This still satisfies D-04/D-05 (`compose.yml` itself is untouched, reversible by deleting one file) while being more discoverable than requiring every command to remember `-f traefik.local.yml`.
4. **A second, independent root cause for login failure exists:** `auth/src/realm-export.json` creates the realm's `admin` user with the realm role `admin` but **no `credentials` array** — the user exists but cannot log in until a password is set via `kcadm.sh set-password`. This is orthogonal to D-01/D-02 (redirect URI mismatch) and must also be fixed for the phase's login-based success condition to be met. `local/set-admin-password.sh` automates this (does not touch `realm-export.json` — stays within D-02's boundary, since it's a runtime `kcadm` call against the already-running realm, not a change to the exported realm data file).
5. **Chrome/Chromium trust the locally-generated CA per-origin, not per-domain-suffix** — even after importing `rootCA.pem`, each subdomain that the browser talks to directly (`eam`, `auth`, `api` via XHR, `room` via WebSocket) may need its own manually-confirmed exception the first time, or data silently stays empty with no visible error outside the browser console. Documented verbatim from the working checkout in `docs/lokale-https-domains.md`.

**Files pulled into this repo from the verified prior art** (content copied 1:1, verified with `docker compose config --quiet` — exit 0):
- `docker-compose.override.yml` — Traefik service (network aliases, local cert mount), `NODE_EXTRA_CA_CERTS` on `server`/`analytics-worker`/`client`, `temporal-ui` certresolver-label neutralization (`:-` fallback quirk, see inline comment), and `mem_limit` caps on `neo4j`/`clickhouse`/`keycloak`/`cube`/`cubestore` (bonus hardening carried over for fidelity with the proven setup — not required by this phase's routing goal, but harmless/reversible and already exercised together with the routing fix).

### Pattern 1: External Traefik network with per-router labels (already implemented)
**What:** Every service that needs Optional Path routing declares `traefik.enable=true` plus `Host()` router rules referencing `${*_SUBDOMAIN}.${BASE_DOMAIN}`, and joins the pre-existing external `traefik` network.
**When to use:** Already fully implemented in `compose.yml` for `neo4j`, `server`, `keycloak`, `excalidraw-room`, `temporal-ui`, `client`. No changes needed.
**Example (existing, unmodified):**
```yaml
# Source: compose.yml (keycloak service, unchanged)
networks:
  - eam-network
  - ${TRAEFIK_NETWORK}
labels:
  - "traefik.enable=true"
  - "traefik.http.routers.${COMPOSE_PROJECT_NAME:-nextgen-eam}-keycloak.rule=Host(`${AUTH_SUBDOMAIN}.${BASE_DOMAIN}`)"
  - "traefik.http.routers.${COMPOSE_PROJECT_NAME:-nextgen-eam}-keycloak.entrypoints=websecure"
  - "traefik.http.routers.${COMPOSE_PROJECT_NAME:-nextgen-eam}-keycloak.tls=true"
  - "traefik.http.routers.${COMPOSE_PROJECT_NAME:-nextgen-eam}-keycloak.tls.certresolver=${TRAEFIK_CERTRESOLVER}"
  - "traefik.docker.network=${TRAEFIK_NETWORK}"
```

### Pattern 2: Local Traefik via `docker-compose.override.yml`, local CA-signed wildcard cert, network aliases on `eam-network` (VERIFIED — the actual, proven fix)
**What:** An auto-merged Compose override that starts a Traefik instance attached to both the existing external `traefik` network (for Docker-provider label discovery) and `eam-network` (with Docker network aliases for every subdomain hostname), presenting a locally-CA-signed wildcard certificate instead of Traefik's bare self-signed default, and mounting that CA into the Node-based services so their own outbound TLS calls trust it.
**When to use:** Always, for this phase — this is the verified, previously-working configuration this phase restores.
**Example (`docker-compose.override.yml`, auto-merged by `docker compose up`, no `-f` needed):**
```yaml
services:
  traefik:
    image: traefik:3.7.8
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "8090:8080" # Dashboard
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./local/traefik/traefik.yml:/etc/traefik/traefik.yml:ro
      - ./local/traefik/dynamic:/etc/traefik/dynamic:ro
      - ./local/certs:/etc/traefik/certs:ro
    networks:
      traefik: {}
      eam-network:
        aliases:
          - eam.example.com
          - api.example.com
          - auth.example.com
          - room.example.com
          - neo4j.example.com
          - temporal.example.com

  server:
    volumes:
      - ./local/certs/rootCA.pem:/etc/ssl/local/rootCA.pem:ro
    environment:
      - NODE_EXTRA_CA_CERTS=/etc/ssl/local/rootCA.pem
  # analytics-worker, client: identical rootCA mount + NODE_EXTRA_CA_CERTS

  temporal-ui: # neutralizes the `${TEMPORAL_UI_CERTRESOLVER:-netcupdns}` fallback quirk for an empty .env value
    labels:
      - "traefik.http.routers.${COMPOSE_PROJECT_NAME:-nextgen-eam}-temporal-ui.tls.certresolver="
```
`local/traefik/traefik.yml` (static config, no ACME) uses the `file` provider pointed at `local/traefik/dynamic/tls.yml`, which declares `local/certs/wildcard.{crt,key}` (produced by `local/make-local-ca.sh`) as the TLS store's `defaultCertificate`.

**Why aliases on `eam-network` (not `traefik`) matter:** `server`/`analytics-worker`/`client` already sit on `eam-network` by default (see `compose.yml`) — aliasing there means these containers resolve `auth.example.com` etc. straight to the local Traefik container via Docker's embedded DNS, with no need for backend services to join the external `traefik` network themselves.
**Why the local CA (not a bare self-signed cert) matters:** a browser can click through an untrusted self-signed certificate warning; a Node.js `https`/`fetch` client (used for the `server` container's own JWKS fetch) cannot — it hard-fails with `UNABLE_TO_VERIFY_LEAF_SIGNATURE` unless the signing CA is explicitly trusted via `NODE_EXTRA_CA_CERTS`.

### Anti-Patterns to Avoid
- **Adding Traefik to `compose.yml`:** Explicitly rejected by D-04/D-05 — Traefik is developer-managed, potentially shared across other local projects (the pre-existing `eam.wien.arthofer.dev` hosts entry is evidence of this). `docker-compose.override.yml` keeps `compose.yml` itself untouched.
- **Assuming `/etc/hosts` (or firewall DNS) alone restores the path:** Browser-side hostname resolution is necessary but not sufficient — the `server` container's own outbound JWKS TLS call also needs (a) a resolvable hostname and (b) an explicitly-trusted certificate; a bare self-signed cert satisfies neither concern for a non-browser client.
- **Editing `auth/src/realm-export.json` to "fix" login:** Out of scope (D-02) — the realm data is already correct; the runtime/proxy layer (and the separate missing-admin-credentials issue, fixed at runtime via `kcadm`, not by editing the exported file) is what's broken.
- **Setting `TRAEFIK_CERTRESOLVER` to a resolver name that isn't registered in the local Traefik's static config:** Harmless (Traefik falls back to its self-signed default cert if no `defaultCertificate` were configured) but produces log noise; prefer leaving it empty for local use — this phase configures an explicit `defaultCertificate` anyway (the local wildcard cert), so this concern is now moot for the browser/JWKS TLS path itself.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Local HTTPS reverse proxy for multiple subdomains | A custom nginx/Caddy config from scratch | Traefik (already the project's chosen technology, images cached locally) | Labels already exist project-wide; adding a second proxy technology would duplicate routing logic and diverge from the K8s ingress story documented in `k8s/README.md`. |
| Self-signed certificate generation | An ad-hoc `openssl req -x509` single cert with no CA, or a third-party tool (`mkcert`) | A hand-rolled local root CA + CA-signed wildcard cert (`local/make-local-ca.sh`, plain `openssl`), trusted explicitly by Node services via `NODE_EXTRA_CA_CERTS` | `[VERIFIED: reference implementation]` — a bare self-signed cert (no CA) cannot be "trusted" by Node's TLS client the way a CA can; `NODE_EXTRA_CA_CERTS` requires a CA certificate, not a leaf cert. This is why D-06's original "self-signed is enough" framing needed correcting (see Verified Prior Art). |
| Container-to-container hostname resolution for public-looking domains | `extra_hosts:` entries duplicated across every backend service in `compose.yml` (would require editing compose.yml, violating D-05) | A single Docker network alias set on the local Traefik container, on `eam-network` (Pattern 2) | One place to declare aliases; automatically visible to every current and future service already on `eam-network` — no `compose.yml` edits needed. |

**Key insight:** The recurring trap in this domain is treating "browser can reach the site" as proof the whole path works. Server-side/backend hostname resolution is a completely separate DNS path (Docker embedded DNS + upstream resolvers) that host `/etc/hosts` never touches.

## Common Pitfalls

### Pitfall 1: "It loads in the browser but login/API calls fail with 401/JWKS errors"
**What goes wrong:** The client loads fine (browser DNS via `/etc/hosts` works, Traefik terminates TLS, static assets and pages render), but any GraphQL call requiring token verification fails, or Keycloak's own token exchange succeeds while the `server` container can't verify tokens.
**Why it happens:** `server` (and `ai-server`/`ai-worker`/`analytics-worker` when profile `ai` is used) resolve `KEYCLOAK_URL=https://auth.example.com` for their own outbound JWKS fetch (`server/src/graphql/schema.ts`, `server/src/auth/auth-jwks.ts`, `ai-server/src/auth/auth-jwks.ts`). Docker containers ignore the host's `/etc/hosts`; the container's DNS query for `auth.example.com` is forwarded to the host's configured upstream DNS, which resolves the *real* public `example.com` — not the local Keycloak.
**How to avoid:** Give the local Traefik container Docker network aliases for every `*.example.com` hostname on `eam-network` (Pattern 2, `docker-compose.override.yml`), AND ensure the CA that signs Traefik's wildcard cert is trusted by Node services via `NODE_EXTRA_CA_CERTS` — a resolvable hostname alone is not sufficient if the cert itself is untrusted by Node's TLS client. Verify DNS with `docker exec nextgen-eam-server-1 getent hosts auth.example.com` (must not be a public IP) and verify trust with `docker compose logs server | grep -i UNABLE_TO_VERIFY` (should be empty).
**Warning signs:** `getent hosts auth.example.com` inside the `server` container returns a public IP (e.g. `93.184.x.x`/`23.192.x.x` range); `docker logs nextgen-eam-server-1` shows JWKS fetch timeouts, TLS certificate mismatches, or connection resets rather than a clean 200 from the local Keycloak.

### Pitfall 2: Traefik logs "unknown certificate resolver" repeatedly, or `temporal-ui` silently reverts to a stale certresolver
**What goes wrong:** Traefik starts and routes traffic (local wildcard cert applies to most routers), but logs are noisy with certresolver errors, or the `temporal-ui` router specifically still tries to use `netcupdns`.
**Why it happens:** `.env`'s `TRAEFIK_CERTRESOLVER=my-traefik-cert-resolver` (template default) references a resolver name the local Traefik's static config never registers (no `--certificatesresolvers.*` flags, per D-06 scope — local uses a `defaultCertificate` instead). Separately, `compose.yml`'s `temporal-ui` label uses `${TEMPORAL_UI_CERTRESOLVER:-netcupdns}` — Compose's `:-` default only triggers for an *unset* variable, not one that is explicitly set to an empty string, so setting `TEMPORAL_UI_CERTRESOLVER=` in `.env` does **not** clear it; the override's dedicated `temporal-ui` labels override is required (see Pattern 2 example).
**How to avoid:** Set `TRAEFIK_CERTRESOLVER=` empty in `.env` for the other routers, and keep the `docker-compose.override.yml` label override that explicitly blanks `temporal-ui`'s certresolver.
**Warning signs:** `docker compose logs traefik` shows repeated `ERR ... certificate resolver ... does not exist` lines, most persistently for the `temporal-ui` router specifically.

### Pitfall 3: Cross-project `/etc/hosts` confusion
**What goes wrong:** Developer assumes the existing `127.0.1.1 eam.wien.arthofer.dev eam` line already covers "eam" and skips adding `eam.example.com`.
**Why it happens:** The bare alias `eam` on that line is unrelated — it does not match `eam.example.com` as a hostname; browsers/resolvers require exact FQDN matches.
**How to avoid:** Add full FQDN entries as a **new** line (do not edit the PVE-managed block), e.g.:
```
127.0.0.1 eam.example.com api.example.com auth.example.com neo4j.example.com room.example.com temporal.example.com
```
**Warning signs:** Browser resolves `eam.example.com` to a public IP or fails to resolve at all (NXDOMAIN) instead of `127.0.0.1`.

### Pitfall 4: Port 443 already bound by another local Traefik/proxy instance
**What goes wrong:** `docker compose up -d` fails with "port is already allocated" for the `traefik` service, or the new Traefik container silently doesn't receive traffic.
**Why it happens:** The developer's machine may already run a shared Traefik instance (for the `eam.wien.arthofer.dev` project) bound to host port 443. Two containers cannot both publish `443:443` on the same host interface.
**How to avoid:** Before starting, check `docker ps --filter publish=443` and `ss -tlnp | grep :443` (verified free at research time on this machine — no process listening on :443). If a shared Traefik instance already exists and is already attached to the `traefik` network, **do not start a second Traefik container** — instead, add the network aliases (Pattern 2) directly to that existing instance's network attachment (`docker network connect --alias eam.example.com --alias auth.example.com ... eam-network <existing-traefik-container>`), since only one process can bind :443.
**Warning signs:** `docker compose up -d` errors with `bind: address already in use` for the `traefik` service.

### Pitfall 5: `ai`-profile services silently broken even after the fix
**What goes wrong:** Core login/GraphQL works after applying the fix, but `ai-server`/`ai-worker`/`analytics-worker` (started only with `docker compose --profile ai up -d`) still fail Keycloak-dependent calls.
**Why it happens:** These three services are attached only to `eam-network` in `compose.yml`, not `${TRAEFIK_NETWORK}` — so even with Traefik aliases configured, these containers have no network path to the local Traefik container at all.
**How to avoid:** Out of scope for this phase's success condition (core login via client + server + keycloak), but document as a known gap for anyone using the `ai` profile with `BASE_DOMAIN=example.com`. Not a regression introduced by this phase — pre-existing compose.yml topology.
**Warning signs:** `ai-server` container logs show JWKS/DNS failures identical to Pitfall 1, even after Traefik aliases are configured.

### Hostname resolution: two supported options

**Option A — `/etc/hosts` (single-machine, always works):**
```
# NextGen EAM local Optional Path (added, does not touch existing PVE block)
127.0.0.1 eam.example.com api.example.com auth.example.com neo4j.example.com room.example.com temporal.example.com
```

**Option B — firewall/router-level DNS (verified on this machine, 2026-07-27):** this developer's LAN firewall/DNS server resolves `eam.example.com` to `192.168.128.166` (this host's real LAN IP, confirmed via `hostname -I`). This works because the host's own `/etc/resolv.conf` points at a **routable** nameserver (`nameserver 192.168.128.1`), not a loopback stub like `systemd-resolved` (`127.0.0.53`) — Docker's embedded DNS forwards unresolved container-side lookups straight to that same routable nameserver, so container-side resolution (the `auth.example.com` JWKS problem) is solved automatically **once all 6 hostnames are registered at the firewall**, without needing `/etc/hosts` at all. **Gap at time of writing: only `eam.example.com` was confirmed registered — `api`/`auth`/`neo4j`/`room`/`temporal.example.com` must get the same `192.168.128.166` A-record, most critically `auth.example.com` (used by both the browser's OIDC redirect and the `server` container's own JWKS fetch).** Verify with `docker exec nextgen-eam-server-1 getent hosts auth.example.com` — must not return a public IP. If the host uses `systemd-resolved`/a loopback resolver instead, Option B does not apply automatically for containers and the network-alias approach (below) becomes required, not just defense-in-depth.

Either option is compatible with the `docker-compose.override.yml` network aliases below, which serve as a robustness fallback regardless of which DNS option is used (protects against future host/network changes).

### Verifying container-side DNS resolution

```bash
docker exec nextgen-eam-server-1 getent hosts auth.example.com
docker exec nextgen-eam-keycloak-1 getent hosts auth.example.com  # sanity check, should match
```

### End-to-end restoration procedure (verified working, per prior-art checkout)
