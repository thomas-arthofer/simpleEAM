# Phase 02.1: Fix diagram sovereignty marker sync gaps - Context

**Gathered:** 2026-07-30
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase fixes two bugs in the sovereignty-marker feature delivered in Phase 2 (`02-04-PLAN.md`/`02-05-PLAN.md`) — it adds no new capability and does not touch the canonical sovereignty evaluator itself:

1. **F5/full-page reload bypasses sovereignty sync entirely.** [DiagramState.ts](../../../client/src/components/diagrams/state/DiagramState.ts)'s localStorage scene-restore path (`loadPersistedScene()` → `setCurrentScene(persistedScene)`) never calls `syncDiagramOnOpen`/`syncSovereigntyMarkers`, unlike `handleOpenDiagram` in [DiagramHandlers.ts](../../../client/src/components/diagrams/handlers/DiagramHandlers.ts), which runs the full sync pipeline (name/missing-element sync + sovereignty markers). Markers only appear via cross-page navigation (`handleOpenDiagram`) or a manual Ctrl+R re-sync — never on a raw browser reload.
2. **Marker ellipses do not live-track a dragged main element.** [sovereigntyMarkers.ts](../../../client/src/components/diagrams/utils/sovereigntyMarkers.ts)'s `createMarkerEllipses` computes fill/ring ellipse `x`/`y` once, at sync time, from the main element's position. The ellipses are only visually grouped (`groupIds: [mainElement.id]`) — not bound via Excalidraw's native `containerId` mechanism (which only supports text-in-shape binding) — so dragging just the main element leaves the markers behind at their old position.

</domain>

<decisions>
## Implementation Decisions

### Reload sync scope
- **D-01 [USER-CONFIRMED 2026-07-30]:** On F5/full-page reload restore, the localStorage scene-restore path in `DiagramState.ts` must run the **full `syncDiagramOnOpen` pipeline** — the same DB name refresh + missing-element detection + `syncSovereigntyMarkers` gate that `handleOpenDiagram` already runs — not a markers-only shortcut. Restore behavior is now identical regardless of how the diagram was opened (URL param, Open dialog, or raw browser reload). This means the restore path also needs whatever `apolloClient`/`selectedCompanyId` context `handleOpenDiagram` relies on, since the current early-mount effect in `DiagramState.ts` runs before some providers may be ready — a research/planning concern, not a further discussion point.

### Live-drag mechanism
- **D-02 [USER-CONFIRMED 2026-07-30]:** Marker ellipses must **live-reposition on every `onChange` event** while the user drags a main element (not just snap into place on drag-end/pointer-up). This is the fuller-fidelity option the user chose over the cheaper "snap at drop" alternative — accept the extra recompute cost on the existing `onChange` handler in `ExcalidrawWrapper.tsx`, which already fires frequently for other reasons.

### Reposition method
- **D-03 [USER-CONFIRMED 2026-07-30]:** When marker positions are recalculated during a drag, **mutate the existing fill/ring ellipse elements in place** (update `x`/`y`, bump `version`/`versionNonce`/`updated`) rather than removing and recreating them via the existing `applySovereigntyMarkers` remove-then-add pattern. Preserves element identity/selection state across drags. Requires a new lightweight reposition function alongside (not replacing) `createMarkerEllipses` — `createMarkerEllipses`/`applySovereigntyMarkers` remain the sync-time (initial/resync) path; the new in-place mutator is drag-time only.

### Drag detection scope
- **D-04 [USER-CONFIRMED 2026-07-30]:** Reposition-on-drag logic only needs to run for main elements that **currently carry marker ellipses** (i.e., elements with an existing fill/ring pair on the canvas right now) — not a lazy "check every dragged database element for markers" condition. Elements without markers attached are skipped entirely, avoiding unnecessary work on every drag/onChange event for unrelated elements.

### the agent's Discretion
- Exact mechanism for locating an element's marker pair during drag (e.g., scanning `customData.mainElementId` vs. maintaining a lookup map) — implementation detail for planning.
- Whether the reload-path full sync reuses `handleOpenDiagram`'s exact code or extracts a shared helper — as long as behavior is identical, per D-01.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `applySovereigntyMarkers` in `sovereigntyMarkers.ts` — existing idempotent remove-then-add logic for sync-time marker placement; stays as-is for initial sync/manual resync, not reused for drag-time repositioning per D-03.
- `handleOpenDiagram` in `DiagramHandlers.ts` — reference implementation for the full sync pipeline the reload path (D-01) must match.

### Established Patterns
- Excalidraw's native `containerId`/`boundElements` binding mechanism (used extensively in `textContainerUtils.ts`, `architectureElements.ts`) only supports **text-bound-to-shape**, not arbitrary shape-follows-shape — confirmed no existing "element A repositions with element B" pattern exists in the diagrams codebase. Marker live-tracking (D-02/D-03) is new ground; there is no direct precedent to copy, only the general idempotent-update convention from `applySovereigntyMarkers`.
- `groupIds: [mainElement.id]` is currently the only linkage between a main element and its marker ellipses beyond `customData.mainElementId` — this grouping lets Excalidraw move them together only if the user drags the group as a multi-selection, not when dragging just the main element alone (the root cause of bug 2).

### Integration Points
- `ExcalidrawWrapper.tsx`'s existing `onChange={handleChange}` is the natural hook point for D-02's live-reposition; no new event wiring needed, only new logic inside/alongside the existing handler chain.
- `DiagramState.ts`'s scene-restore effect currently runs early on mount (gated only by `openDiagramId` being absent) — D-01's full-sync fix needs `apolloClient` and `selectedCompanyId` (from `useCompanyContext`) to be available at that point; verifying/sequencing this is a planning-time concern, not a further gray area.

</code_context>
