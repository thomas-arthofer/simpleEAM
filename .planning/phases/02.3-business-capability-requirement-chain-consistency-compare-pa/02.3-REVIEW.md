# Phase 02.3: Code Review Report

**Reviewed:** 2026-08-03
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The parent-vs-child required-level contradiction tracer is well-structured and the classifier itself (`classifyCapabilityAgainstParent`) correctly implements the D-02/D-03/D-04 null-exclusion and multi-parent-independence rules — verified by tracing Tests A–D, G–L by hand against the code. The Cypher change in `repository.ts` is **not** vulnerable to injection (all interpolation is static clause selection gated by a boolean, never by untrusted data) and the tenant-isolation guard for the new parent match is sound (T-02.3-04 correctly mitigated: an out-of-tenant parent is dropped from `collect(DISTINCT parent {...})` because Neo4j's per-row `OPTIONAL MATCH ... WHERE` semantics discard the failing candidate row rather than nulling only part of the pattern).

However, one real correctness bug was found in `markers.ts`: the narrow YELLOW-self exception can be **silently clobbered back to GREY** for a `BusinessCapability` that is shared by two or more parents within the same analyzed subtree (a "diamond" shape, which the codebase explicitly supports and tests for `Infrastructure`/`Application` nodes) — the final `selfStatus` becomes dependent on iteration order of `analysis.findings` rather than being computed from the full finding set. A second issue was found in `evaluator.ts`: the new `classifyCapabilityAgainstParent` call inside `analyzeCapabilitySubtree` is not guarded by the recursion's cycle-safety `visited` set, so a cyclic `childCapabilities` edge can still produce a spurious contradiction finding (it cannot cause infinite recursion, but it does violate the D-03 "stops silently, no finding" contract) — and the phase's own cycle-safety regression test (Test M) does not actually exercise this path, giving false confidence.

## Critical Issues

### CR-01: `markers.ts` can silently overwrite a capability's genuine YELLOW self-violation back to GREY for diamond-shared capabilities

**File:** [server/src/sovereignty/markers.ts](server/src/sovereignty/markers.ts#L77-L108)
**Issue:**
In the main findings loop, whether a capability keeps its self-violation status is decided **per finding, locally**, not from the full set of findings for that id:

```ts
const isCapabilitySelfViolation =
  isCapability && isViolatingElement && finding.violatingElementType === 'businessCapability'

markers.set(id, {
  selfStatus: isCapabilitySelfViolation
    ? worseStatus(current.selfStatus, finding.status)
    : isCapability
      ? 'GREY'                                   // <-- unconditional reset
      : isViolatingElement
        ? worseStatus(current.selfStatus, finding.status)
        : current.selfStatus,
  ...
})
```

`BusinessCapability` supports multiple parents (`HAS_PARENT` `[BusinessCapability!]!`), and the codebase's own design intent explicitly supports "a capability shared by two different parents (diamond shape)... evaluated independently on each path" (see the JSDoc above `analyzeCapabilitySubtree` and the existing `multiParentInfrastructureFixture` test for the analogous `Infrastructure` case). Because the evaluator has **no memoization** (by design, so each parent edge is judged independently per D-02), a capability `C` that is a `childCapabilities` entry of both `P1` and `P2` (both inside the same analyzed root's subtree) is analyzed **twice**, producing two separate blocks of findings in `analysis.findings`:

- Block for `P1`: `C`'s own findings (passthrough, non-violating) ... then `C`-vs-`P1` contradiction (`C` IS the violating element, businessCapability-typed) — self-violation is always pushed **last** within a block (see `evaluator.ts` lines 303–320).
- Block for `P2`: `C`'s own findings recomputed fresh (passthrough again) ... then, **only if `C` also violates against `P2`**, a `C`-vs-`P2` contradiction.

If `C` violates against `P1` but is compliant against `P2` (a very plausible real-world case — different parents can have different, stricter-or-looser requirements), `P2`'s block ends with a **passthrough** finding for `C`, not a self-violation. If `P2`'s block is processed after `P1`'s block (which happens whenever `P2` appears after `P1` in `chain.childCapabilities`, or is nested under a later-processed ancestor), the loop's `isCapability ? 'GREY'` branch **unconditionally overwrites** `C`'s already-correct `YELLOW` self-status back to `GREY` — and nothing after it restores it, since `C` has no further self-violation entry in `P2`'s block.

The bottom-of-function backfill loop does **not** fix this:

```ts
const capabilitiesWithOwnFinding = new Set(
  analysis.findings
    .filter(f => f.violatingElementType === 'businessCapability')
    .map(f => f.violatingElementId)
)
for (const id of capabilityIds) {
  const current = ensure(id)
  if (capabilitiesWithOwnFinding.has(id)) continue   // <-- C is in this set, so it's skipped ("continue"), leaving the clobbered GREY in place
  ...
}
```

`C` is a member of `capabilitiesWithOwnFinding` (it *did* self-violate somewhere), so the backfill loop `continue`s past it instead of restoring the correct value — the incorrect `GREY` from the `P2` block's last write stands as the final marker.

**Impact:** A capability with a genuine, real, correctly-computed YELLOW contradiction finding (present in `analysis.findings`, so the detail-view findings list is correct) can render as neutral GREY in the diagram marker / summary status depending on unrelated sibling ordering — exactly the feature this phase was built to deliver, silently failing for a documented, supported topology.

**Fix:** Compute the "does this id have any self-violation anywhere in the whole analysis" set **once, up front** (reusing the same `filter`/`map` logic already used for the backfill loop) and consult it in the main loop's branch instead of the purely-local, per-finding check:

```ts
const selfViolatingIds = new Set(
  analysis.findings
    .filter(f => f.violatingElementType === 'businessCapability')
    .map(f => f.violatingElementId)
)

// ... inside the loop:
const isCapabilitySelfViolation = isCapability && selfViolatingIds.has(id)
markers.set(id, {
  selfStatus: isCapabilitySelfViolation
    ? (isViolatingElement ? worseStatus(current.selfStatus, finding.status) : current.selfStatus)
    : isCapability
      ? 'GREY'
      : isViolatingElement
        ? worseStatus(current.selfStatus, finding.status)
        : current.selfStatus,
  ...
})
```
This makes the branch order-independent: once `id` is known (globally) to have a self-violation, no other finding referencing it as a mere passthrough member can reset it to GREY. The single `selfViolatingIds` set can then also replace `capabilitiesWithOwnFinding` at the bottom.

**Note on test coverage:** none of the new tests (`markers.test.ts` Tests E/F) exercise a capability with 2+ parents inside the same subtree, so this regression would not have been caught. Recommend adding a fixture where a `childCapabilities` entry is reachable from two different branches (or, simpler, from two entries of the same parent's `childCapabilities` array referencing the same `rootId`) with a self-violation against only one of them.

## Warnings

### WR-01: `classifyCapabilityAgainstParent` call in `analyzeCapabilitySubtree` is not gated by the cycle-safety `visited` set

**File:** [server/src/sovereignty/evaluator.ts](server/src/sovereignty/evaluator.ts#L290-L321)
**Issue:** The recursive descent correctly stops on a cyclic edge:

```ts
function analyzeCapabilitySubtree(chain, visited) {
  if (visited.has(chain.rootId)) return { findings: [], capabilityIds: [] }   // line 294
  ...
  for (const child of chain.childCapabilities) {
    const nested = analyzeCapabilitySubtree(child, pathVisited)               // line 304 — silently empty if `child` is already visited
    ...
    descendantFindings.push(
      ...classifyCapabilityAgainstParent(child, { id: chain.rootId, required: chain.required }, []) // line 318 — NOT guarded by `visited`/`pathVisited` at all
    )
  }
  ...
}
```

`nested` correctly comes back empty when `child.rootId` is already in `visited` (D-03's "stops silently" contract holds for the recursive walk). But the new `classifyCapabilityAgainstParent(child, ...)` call at line 318 runs **unconditionally** for every entry in `chain.childCapabilities`, including one that is a cycle-back to an already-visited ancestor. This does not cause infinite recursion or a stack overflow (the function itself is not recursive), but it does mean a cyclic `HAS_PARENT` edge can still produce a **spurious contradiction finding** comparing the re-entrant node's required levels against its immediate (cyclic) "parent" — something D-03's design intent (`.planning/phases/02-canonical-sovereignty-evaluation-ux-diagnostics/02-CONTEXT.md`: "re-entering one of them stops silently — no finding, no recursion") explicitly says should not happen.

**Reproduction:** using a variant of `capabilityCycleFixture` (`server/src/sovereignty/__tests__/fixtures.ts`) where the cyclic re-entrant node's `required.security` is set to a value *weaker* than its immediate (cyclic) parent's `required.security` (the current fixture uses `HIGH` vs. `LOW`, which happens not to trigger the contradiction — see WR-02), the same fixture shape would produce an extra `YELLOW` finding attributing a tree contradiction to an already-visited/cyclic node.

**Fix:** Skip the `classifyCapabilityAgainstParent` call when the child is already in `visited` (mirroring the same guard used for the recursive `nested` call), e.g.:

```ts
for (const child of chain.childCapabilities) {
  if (visited.has(child.rootId)) continue  // stay silent for cyclic edges, per D-03
  const nested = analyzeCapabilitySubtree(child, pathVisited)
  ...
  descendantFindings.push(
    ...classifyCapabilityAgainstParent(child, { id: chain.rootId, required: chain.required }, [])
  )
}
```
(Note `analyzeCapabilitySubtree(child, pathVisited)` already internally no-ops when `child.rootId` is in `pathVisited`/`visited`, so this is a cheap, purely-defensive addition that also skips the now-redundant `classifyCapabilityAgainstParent` call for the same case.)

### WR-02: Test M does not actually exercise the vulnerable path described in WR-01, giving false confidence in cycle-safety

**File:** [server/src/sovereignty/__tests__/evaluator.test.ts](server/src/sovereignty/__tests__/evaluator.test.ts#L269) (Test M, `'terminates on a childCapabilities cycle and still emits the non-cyclic descendant finding'`) and [server/src/sovereignty/__tests__/fixtures.ts](server/src/sovereignty/__tests__/fixtures.ts) (`capabilityCycleFixture`)
**Issue:** `capabilityCycleFixture`'s cyclic re-entrant node has `required.security = 'HIGH'` and its immediate (cyclic) "parent" (`cap-cycle-child`) has `required.security = 'LOW'`. Since `HIGH` is *not* weaker than `LOW`, `classifyCapabilityAgainstParent` produces **no finding** for the cyclic edge regardless of whether it is correctly guarded — the test would pass identically whether or not WR-01 is fixed. The test also only asserts on the existence of the expected non-cyclic finding via `.find(...)`; it never asserts `result.findings.length` or the absence of an unexpected finding referencing the cyclic node (`violatingElementId === 'cap-cycle-root'` appearing a second time via the re-entrant path), so even a spurious extra finding would not fail the test.
**Fix:** Add an assertion on the total finding count (or explicitly assert no finding names the cyclic node as a violating element via the re-entrant edge), and/or add a second cycle fixture where the cyclic node's required level genuinely *would* trigger a contradiction against its immediate parent, to prove the guard from WR-01 is in place.

## Info

### IN-01: `violatingElementName: chain.rootId` displays a raw id instead of a human-readable name

**File:** [server/src/sovereignty/evaluator.ts](server/src/sovereignty/evaluator.ts#L115)
**Issue:** Every other node type (`ApplicationNode`, `InfrastructureNode`, `AIComponentNode`) carries a real `.name` field, and `classifyNode`'s findings use it (`violatingElementName: node.name`). `BusinessCapabilityChain`/`SupportChain` has no `name` field at all, so `classifyCapabilityAgainstParent` falls back to `chain.rootId` for `violatingElementName`. This is explicitly called out and accepted in `02.3-01-PLAN.md`'s `<action>` block ("there is no `name` on `SupportChain` today — use `rootId` as the name; a follow-up phase can plumb a real name if needed"), so it's a deliberate, documented deviation rather than an oversight — flagging here only so it isn't lost as a UX debt item (a findings list showing a raw capability id like `cap-root-weaker` instead of "Order Management" is a real, user-facing quality gap for this finding type specifically).
**Fix:** Track as a follow-up: thread a `name` field onto `SupportChain`/`BusinessCapabilityChain` (populated by `repository.ts` from `cap.name`) so `violatingElementName` can be a real display name, matching every other node type.

### IN-02: `chainPathPrefix` parameter on `classifyCapabilityAgainstParent` is always called with `[]`

**File:** [server/src/sovereignty/evaluator.ts](server/src/sovereignty/evaluator.ts#L98-L101)
**Issue:** Both call sites (`analyzeBusinessCapability` line 337, `analyzeCapabilitySubtree` line 318) pass a literal `[]` for `chainPathPrefix`. The parameter exists to "support later reuse from the descendant recursion path" per the 02.3-01 plan, but Plan 02.3-02 wired the descendant case by re-prefixing the *entire* returned finding array one level at a time in the caller instead of ever populating this parameter — so it is currently dead weight (always `[]` at every call site in the codebase). Not a functional bug, but worth simplifying or documenting why it's kept for future extensibility.
**Fix:** Either remove the parameter (inline `[]` at the two call sites) or add a one-line comment noting it is deliberately reserved for a not-yet-implemented future call pattern, so a future reader doesn't waste time looking for a call site that actually uses a non-empty prefix.

### IN-03: A parent capability that exists but has no `OWNED_BY` edge is silently excluded from `parentRequiredLevels` (fail-closed, not a leak, but a data-integrity gap)

**File:** [server/src/sovereignty/repository.ts](server/src/sovereignty/repository.ts#L290-L293)
**Issue:** The new clause is a single combined Cypher pattern:
```cypher
OPTIONAL MATCH (cap)-[:HAS_PARENT]->(parent:BusinessCapability)-[:OWNED_BY]->(parentCompany:Company)
WHERE parent IS NULL OR $isAdmin OR parentCompany.id IN $companyIds
```
Because `parent` and `parentCompany` are bound by a single multi-hop pattern, a parent capability that exists but has *no* `OWNED_BY` relationship at all (a data-integrity issue, e.g. an orphaned capability) causes the **entire** pattern to fail to match for that parent, silently excluding it from `parentRequiredLevels` — even for an admin caller, and even though `parent IS NULL` only covers the "no `HAS_PARENT` edge at all" case, not "parent exists but is unowned". This is safe from a tenant-isolation standpoint (fails closed, never leaks), but it means the D-01 contradiction check would silently never fire against such a parent, which could mask a real, intended requirement-tree contradiction if company data is incomplete.
**Fix:** Optional/low-priority — if orphaned (unowned) `BusinessCapability` nodes are expected to occur in practice, consider an `isAdmin`-only fallback path that still surfaces the parent's required levels even without a resolvable owning company, since an admin is allowed to see everything regardless of ownership.
