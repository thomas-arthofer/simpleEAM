# Phase 02.3 Plan 02: Descendant/Multi-Parent Contradiction Coverage + Neo4j Parent Fetch Summary

**Wires Plan 02.3-01's parent-vs-child contradiction tracer end-to-end: `analyzeCapabilitySubtree` now flags any nested capability whose required level is weaker than its immediate in-scope parent (D-01 descendant half), multi-parent independence (D-02) is verified against `walkInfrastructure`'s established pattern, and `fetchBusinessCapabilityChain`'s Cypher query now fetches the analysis root's real direct parents' required levels from Neo4j (with a tenant-isolation guard, T-02.3-04) — the feature now fires on live GraphQL queries, not just hand-built fixtures.**

## Accomplishments

- `evaluator.ts`: `analyzeCapabilitySubtree`'s existing per-child recursion loop now also calls `classifyCapabilityAgainstParent(child, { id: chain.rootId, required: chain.required }, [])` for every child, comparing the child directly against its immediate in-scope parent — no new recursion, no changes to the D-03 cycle-safety visited-set contract. The resulting finding is pushed directly (not re-prefixed like `nested.findings`), since `classifyCapabilityAgainstParent` already produces the correct `[chain.rootId, child.rootId]` chainPath for that recursion level. Multi-level chains (grandchild vs. child) work automatically: the grandchild's finding is created one level down and rolls up through the pre-existing re-prefix loop, producing a full `[root, child, grandchild]` path.
- Verified (Tests K/L) that Plan 02.3-01's `chain.parentRequiredLevels.flatMap(...)` loop in `analyzeBusinessCapability` already implements D-02's independent-per-parent iteration correctly — two stricter parents produce two findings; only-one-stricter produces exactly one. No refactor was needed.
- `repository.ts`: `fetchBusinessCapabilityChain` gained an `isRoot` parameter (default `false`), gating a new OUT-direction Cypher clause `(cap)-[:HAS_PARENT]->(parent:BusinessCapability)-[:OWNED_BY]->(parentCompany:Company) WHERE parent IS NULL OR $isAdmin OR parentCompany.id IN $companyIds` and its `parentRequiredRows` RETURN column — included in the query text only when `isRoot` is true, so recursive `childId` calls never execute the parent match at all. `loadBusinessCapabilitySupportChain` (the entry point) now passes `isRoot: true`. The tenant-isolation guard mirrors the existing root-level `OWNED_BY` check exactly, mitigating T-02.3-04 (a parent from another company's tenant would have `parent`/`parentCompany` nulled for that expansion and get silently dropped by `collect(DISTINCT ...)`).
- `fixtures.ts`/`evaluator.test.ts`: added `descendantParentContradictionFixture` (3-level root→child→grandchild), `multiParentBothStricterFixture`, `multiParentOnlyOneStricterFixture`, and `capabilityCycleFixture`, plus Tests G–M covering the descendant hook, null exclusion on both sides, the grandchild-compares-against-immediate-parent rule, D-02 multi-parent independence, and a cycle-safety regression check.
