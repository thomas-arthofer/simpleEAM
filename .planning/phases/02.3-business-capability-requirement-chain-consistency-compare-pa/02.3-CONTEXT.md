# Phase 02.3: Business capability requirement-chain consistency: compare parent vs child BusinessCapability required levels - Context

**Gathered:** 2026-08-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Compare a `BusinessCapability`'s own sovereignty **required** levels against its parent `BusinessCapability`'s **required** levels along `HAS_PARENT` edges — this is a required-vs-required tree-consistency check, distinct from the existing achieved-vs-required evaluation. When a child's required level is weaker (lower maturity) than its parent's for a dimension, that is a self-status finding on the **child**, exposed as `YELLOW` (not `RED` — no actual achieved-value violation occurred, only a structural contradiction in the requirement tree itself). This extends D-05 (`.planning/phases/02-canonical-sovereignty-evaluation-ux-diagnostics/02-CONTEXT.md`), which today forces `selfStatus: GREY` unconditionally for every capability — this phase adds one specific, scoped exception where a capability CAN be its own violation source.

</domain>

<decisions>
## Implementation Decisions

### Comparison Scope
- **D-01:** The capability the user is currently viewing (the analysis root) is ALSO checked against its own real parent(s) above it — not just descendants-within-the-subtree checked against a parent already known during the downward walk. This requires a new upward fetch in `repository.ts` of the root's direct parent(s)' required levels (only the required levels are needed, not each parent's full support chain). — **Reversibility:** costly — touches the repository fetch shape (`BusinessCapabilityChain` gains a "parent required levels" input) and the evaluator's entry point for every root, not just descendants.

### Multi-Parent Handling
- **D-02:** A `BusinessCapability` can have multiple parents (`parents: [BusinessCapability!]! @relationship(HAS_PARENT, OUT)`). A child is flagged if its required level is below **ANY** parent's required level for a dimension (equivalent to comparing against the strictest/max parent requirement). It is NOT required to be below ALL parents.

### Null-Required Semantics
- **D-03:** If the parent's requirement for a dimension is `null` (not set), that dimension is excluded from comparison entirely for that child — mirrors `classifyNode`'s existing rule that a check only fires when the requirement side being compared FROM is explicitly set.
- **D-04:** If the parent HAS a requirement set but the child's own requirement is `null` (never assigned), this is **excluded** — NOT flagged as a contradiction. Comparison only applies when **both** parent and child have an explicit (non-null) requirement for that dimension. (User explicitly chose exclusion over treating child-null as "weakest", diverging from the agent's initial recommendation.)

### Self-Status & Marker UI
- **D-05 [extends Phase 2's D-05]:** A capability with a parent-requirement contradiction DOES show a colored `YELLOW` fill ellipse on diagrams — breaking the current UI-SPEC invariant that a `BusinessCapability` fill is always neutral grey. This is a deliberate, narrow exception: only capabilities with this specific tree-contradiction finding get a colored fill; all other capabilities keep the neutral grey fill (D-05 from Phase 2 still holds for the achieved-value case). — **Reversibility:** costly — `markers.ts`'s `projectMarkers` currently hard-codes `selfStatus: 'GREY'` unconditionally for every id in `capabilityIds`; this must become conditional, and `markers.test.ts` has existing assertions ("capability ring only", "every nested BusinessCapability child a GREY selfStatus") that must be updated to allow this one exception without weakening the general rule.
- **D-06:** The new finding reuses the existing `Finding` shape as-is — no new DTO/finding-type. `requiredLevel` = the parent's required level, `actualLevel` = the child's own required level (repurposed field, since there is no "achieved" value in this comparison). `violatingElementType` is extended to include `'businessCapability'` (today it's `'application' | 'aiComponent' | 'infrastructure'` only). `chainPath` is `[parentId, childId]` (or the relevant ancestor path when the root-parent check from D-01 applies).

### the agent's Discretion
- Exact GraphQL schema/enum wiring for the new `'businessCapability'` violatingElementType value, and how the repository fetches "root's own direct parent(s) required levels only" without pulling their full support chains, are implementation details for planning/research to resolve.
- UI wording for this finding in the existing findings list (e.g., how "required X, actual Y" reads when both sides are "required" levels) is left to planning/research to phrase sensibly — no new field was requested, just sensible reuse of existing labels.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `classifyNode` in `evaluator.ts` already implements the required-vs-actual-with-null-semantics comparison pattern this phase needs (parent-required vs child-required), just against a different pair of values — can likely be adapted or paralleled rather than reinvented.
- `worseStatus`/`STATUS_RANK` in `markers.ts` already ranks `GREEN < GREY < YELLOW < RED` and is reused wherever multiple findings must be reconciled to one worst status — the new YELLOW findings flow through this unchanged.
- `aggregateDownstreamStatus` in `evaluator.ts` already handles YELLOW in its precedence chain (RED > YELLOW > GREY > GREEN), even though YELLOW was never actually produced before this phase — no change needed there.

### Established Patterns
- Per-path visited-set cycle safety (D-03, Phase 2): any new upward-walk logic (D-01) must follow the same "each branch gets its own copy of the visited set" contract used by `walkInfrastructure`/`walkApplication`/`analyzeCapabilitySubtree`.
- Per-fetch memoization (`NodeCache`/`inFlight` in `repository.ts`): a new upward parent-fetch should reuse this cache so a capability referenced as both a subtree member and someone's upward parent is only queried once.
- One classifier, reused everywhere (RESEARCH.md Anti-Pattern 3): this phase's new finding type must flow through the same `Finding[]` → `projectMarkers` → detail view / diagram marker pipeline as every other finding — no separate parallel check.

### Integration Points
- `SovereigntyAnalysis.findings` (flat array) is what both the detail view and diagram markers already consume — the new tree-contradiction findings need no new top-level field, just new entries in this array with `violatingElementType: 'businessCapability'`.
- `projectMarkers`'s current unconditional GREY-self backfill loop over `capabilityIds` (`markers.ts`) is the single place that needs to become conditional per D-05.

</code_context>
