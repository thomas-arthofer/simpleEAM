### `server/src/sovereignty/evaluator.ts` (service, transform)

**Analog 1 — required-vs-required comparison with null-semantics:** `classifyNode` (lines 42-83) already implements the exact null-semantics shape D-03/D-04 describe, just for achieved-vs-required. The new comparison is required-vs-required (parent vs child), so this is a close structural parallel, not a literal reuse (the "actual is null → GREY" branch does NOT apply here per D-04 — a null child-required is EXCLUDED, not flagged).

```typescript
export function classifyNode(
  node: ClassifiableNode,
  required: RequirementLevels,
  chainPath: readonly string[]
): Finding[] {
  const findings: Finding[] = []
  const fullPath = [...chainPath, node.id]

  for (const dimension of SOVEREIGNTY_DIMENSIONS) {
    const requiredLevel = required[dimension]
    const actualLevel = node.achieved[dimension]

    if (actualLevel === null) {
      findings.push({
        violatingElementId: node.id,
        violatingElementType: node.type,
        violatingElementName: node.name,
        dimension,
        status: 'GREY',
        requiredLevel,
        actualLevel: null,
        chainPath: fullPath,
      })
      continue
    }

    if (requiredLevel !== null && maturityIndex(actualLevel) < maturityIndex(requiredLevel)) {
      findings.push({
        violatingElementId: node.id,
        violatingElementType: node.type,
        violatingElementName: node.name,
        dimension,
        status: 'RED',
        requiredLevel,
        actualLevel,
        chainPath: fullPath,
      })
    }
  }

  return findings
}
```

**Divergence for the new function (per D-03/D-04/D-05/D-06):** the new function (e.g. `classifyCapabilityAgainstParent`) must:

- Skip the dimension entirely (no finding, not even GREY) when EITHER side is `null` — unlike `classifyNode`'s "actual null → GREY" branch, which does not apply here (D-04: "excluded — NOT flagged").
- Only flag when `maturityIndex(childRequired) < maturityIndex(parentRequired)` (mirrors the `requiredLevel !== null && maturityIndex(actual) < maturityIndex(requiredLevel)` guard shape at line 76, but comparing two required values, not required-vs-achieved).
- Emit `status: 'YELLOW'` (not `'RED'`), `violatingElementType: 'businessCapability'`, `violatingElementId`/`violatingElementName` = the CHILD, `requiredLevel` = the PARENT's required level, `actualLevel` = the CHILD's own required level (D-06's explicit field repurposing).
- `maturityIndex` (lines 27-29) is reusable as-is for comparing two `SovereigntyMaturityLevel` values.

**Analog 2 — multi-parent independent-edge iteration (D-02):** `walkInfrastructure`'s loop over multiple `parentInfrastructure` edges (lines 101-119) is the direct structural analog for D-02's "flagged if below ANY parent" rule — each parent edge is evaluated independently and pushes its own finding, never collapsed into one synthetic "worst of" comparison:

```typescript
function walkInfrastructure(
  infra: InfrastructureNode,
  required: RequirementLevels,
  chainPath: readonly string[],
  visited: ReadonlySet<string>
): Finding[] {
  if (visited.has(infra.id)) return []

  const pathVisited = new Set(visited)
  pathVisited.add(infra.id)
  const nextPath = [...chainPath, infra.id]

  const findings = classifyNode(infra, required, chainPath)

  for (const parent of infra.parentInfrastructure) {
    findings.push(...walkInfrastructure(parent, required, nextPath, pathVisited))
  }

  return findings
}
```

For the new root-vs-parents check, the equivalent shape is a simple `for (const parent of chain.parentRequiredLevels) { findings.push(...classifyCapabilityAgainstParent(chain, parent, ...)) }` — no recursive visited-set walk is needed here since D-01 only fetches DIRECT parents (one level), not a recursive upward walk, so the cycle-safety concern from `walkInfrastructure` (re-entering an already-visited ancestor) does not apply to this specific, narrower feature. Still follow the "never collapse multiple parents into one worst-of finding" contract this analog demonstrates.

**Analog 3 — where descendant-vs-parent comparisons should hook in:** `analyzeCapabilitySubtree` (lines 247-268) already recurses through every `child` in `chain.childCapabilities`, and at each recursion the PARENT's own `chain.required` is already in scope as a plain function parameter — no new fetch is needed for descendant-vs-parent comparisons, only for the ROOT's own upward parents (D-01: "not just descendants-within-the-subtree checked against a parent already known during the downward walk"):

```typescript
function analyzeCapabilitySubtree(
  chain: BusinessCapabilityChain,
  visited: ReadonlySet<string>
): CapabilitySubtreeResult {
  if (visited.has(chain.rootId)) return { findings: [], capabilityIds: [] }

  const pathVisited = new Set(visited)
  pathVisited.add(chain.rootId)

  const ownFindings = collectOwnFindings(chain)

  const descendantFindings: Finding[] = []
  const capabilityIds: string[] = [chain.rootId]
  for (const child of chain.childCapabilities) {
    const nested = analyzeCapabilitySubtree(child, pathVisited)
    for (const finding of nested.findings) {
      descendantFindings.push({ ...finding, chainPath: [chain.rootId, ...finding.chainPath] })
    }
    capabilityIds.push(...nested.capabilityIds)
  }

  return { findings: [...ownFindings, ...descendantFindings], capabilityIds }
}
```

The new child-vs-parent check belongs in this loop: for each `child`, compare `child.required` against `chain.required` (the parent already in scope) using the new `classifyCapabilityAgainstParent`-style function, and prepend to `descendantFindings` alongside the existing nested-rollup findings — reusing the SAME `chainPath` re-prefixing convention already shown (`[chain.rootId, ...finding.chainPath]`).

**Analog 4 — entry point wiring:** `analyzeBusinessCapability` (lines 279-288) is where the ROOT's own upward parent-check (D-01, using the new `chain.parentRequiredLevels` from repository.ts) must be added — merged into the `findings` array alongside what `analyzeCapabilitySubtree` already returns:

```typescript
export function analyzeBusinessCapability(chain: BusinessCapabilityChain): SovereigntyAnalysis {

```

`aggregateDownstreamStatus` (lines 85-90) already ranks `RED > YELLOW > GREY > GREEN` and needs NO change — it already handles YELLOW in its precedence chain per the CONTEXT.md note, even though nothing produced YELLOW before this phase.

### `server/src/sovereignty/markers.ts` (service/aggregator, transform)

**Analog:** the file's own existing unconditional GREY backfill loop and the `isCapability` branch inside the findings loop — both must become conditional per D-05's "one specific, scoped exception."

**Current unconditional backfill (lines 105-112) — the primary target of this phase's D-05 change:**

```typescript
// A BusinessCapability with zero findings anywhere in its own subtree
// (fully compliant, e.g. a compliant sibling next to a violating one)
// never appears in the loop above at all, so without this it would fall
// through to `resolveMarker`'s DEFAULT_MARKER (GREEN/GREEN) — wrong for a
// capability, which must always resolve GREY-self, never GREEN-self
// (D-05). Backfills every capability id with an explicit GREY-self entry,
// defaulting its downstream to GREEN only when no finding ever touched it.
for (const id of capabilityIds) {
  const current = ensure(id)
  markers.set(id, { selfStatus: 'GREY', downstreamStatus: current.downstreamStatus })
}
```

This forces `selfStatus: 'GREY'` for EVERY id in `capabilityIds`, unconditionally overwriting whatever `selfStatus` the findings loop above may have already computed for that same id. Per this phase's D-05, this must become conditional: only force GREY when the capability has no `violatingElementType: 'businessCapability'` finding naming it as `violatingElementId`; otherwise, preserve/apply the worse-of-GREY-and-YELLOW status already computed.

**Current findings-loop branch that hard-codes capability GREY (lines 77-99), the other place this phase's exception must be threaded through:**

```typescript
for (const finding of analysis.findings) {
  for (const id of finding.chainPath) {
    // Every BusinessCapability in this analysis's own subtree (D-11) must
    // stay GREY-self forever, not just the outermost query root (D-05): a
    // capability owns no achieved rating, whether it's the id the caller
    // asked about or a nested `childCapabilities` id merely passed through
    // on the way to a descendant's violation. Without this, a nested
    // capability's selfStatus fell back to the DEFAULT_MARKER's GREEN,
    // since it is never a finding's own `violatingElementId` (only
    // Application/AIComponent/Infrastructure ever are).
    const isCapability = capabilityIds.has(id)
    const current = ensure(id)
    const isViolatingElement = id === finding.violatingElementId

    markers.set(id, {
      selfStatus: isCapability
        ? 'GREY'
        : isViolatingElement
          ? worseStatus(current.selfStatus, finding.status)
          : current.selfStatus,
      downstreamStatus: worseStatus(current.downstreamStatus, finding.status),
    })
  }
}
```

Per D-05/D-06, `isCapability ? 'GREY' : ...` needs a new branch: when `isCapability && isViolatingElement && finding.violatingElementType === 'businessCapability'`, `selfStatus` should be `worseStatus(current.selfStatus, finding.status)` (i.e. YELLOW) instead of the hard-coded GREY — but for every OTHER capability id in the chain path (the ones merely passed through, not the violating capability itself), the existing `isCapability ? 'GREY'` branch must remain unchanged (D-05 explicitly: "only capabilities with this specific tree-contradiction finding get a colored fill; all other capabilities keep the neutral grey fill").

`worseStatus`/`STATUS_RANK` (lines 22-32) require NO change — `GREEN < GREY < YELLOW < RED` already ranks YELLOW above GREY, so `worseStatus('GREY', 'YELLOW')` already resolves to `'YELLOW'` correctly:

```typescript
const STATUS_RANK: Record<SovereigntyStatus, number> = {
  GREEN: 0,
  GREY: 1,
  YELLOW: 2,
  RED: 3,
}

function worseStatus(a: SovereigntyStatus, b: SovereigntyStatus): SovereigntyStatus {
  return STATUS_RANK[b] > STATUS_RANK[a] ? b : a
}
```
